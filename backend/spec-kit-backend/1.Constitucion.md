# Constitución del Backend — Hotel Gran Capital

## Objetivo

Construir una API REST segura y mantenible para gestionar usuarios, clientes, habitaciones, reservas, pagos, check-in, check-out, servicios adicionales y reportes del Hotel Gran Capital.

## Tecnologías obligatorias

- TypeScript estricto.
- Node.js.
- Hono.js para HTTP REST.
- PostgreSQL mediante `pg`.
- JWT firmado y verificado mediante `jose`.
- `bcrypt` con exactamente 8 rondas.
- Zod para validar body, params, query y variables de entorno.
- Variables de entorno mediante `.env`.

## Arquitectura

```text
HTTP / Presentación
  routes → middlewares → controllers
                    ↓
             services / negocio
                    ↓
          repositories / pg
                    ↓
                PostgreSQL
```

Los Controllers no acceden a PostgreSQL. Los Services no dependen de Hono. Los Repositories no contienen lógica HTTP ni de presentación.

## Entidades y relaciones

El backend reutiliza las tablas actuales: `clientes`, `personal`, `habitaciones`, `reservas`, `pagos`, `servicios_adicionales` y `solicitudes_servicio`.

- `clientes`: cuenta y datos del huésped. Su rol lógico es `CLIENTE`.
- `personal`: cuentas de `ADMINISTRADOR` y `RECEPCIONISTA`.
- `reservas`: pertenece a un cliente y una habitación.
- `pagos`: relación uno a uno con reserva mediante `UNIQUE(id_reserva)`.
- `solicitudes_servicio`: relaciona reserva, cliente y servicio.

Una reserva puede tener muchas solicitudes. Una habitación puede tener reservas en distintos períodos, pero no períodos superpuestos. Check-in cambia la habitación a `OCUPADA`; check-out completa la reserva y cambia la habitación a `LIMPIEZA`.

```text

POST /auth/logout
GET|POST|PUT /usuarios
GET|POST|PUT /habitaciones
GET|POST|PUT /clientes
GET|POST|PUT /reservas
POST /reservas/:id/checkin
POST /reservas/:id/checkout
PATCH /reservas/:id/cancelar
GET|POST /pagos
GET|POST|PUT /servicios
GET|POST|PUT /solicitudes-servicio
GET /reportes/dashboard
GET /reportes/reservas
GET /reportes/ocupacion
GET /reportes/pagos
```

## Autenticación

El login busca clientes y personal, compara la contraseña con `bcrypt.compare`, y genera un JWT con `jose` (`HS256`, `sub`, `rol`, `iat`, `exp`). `BCRYPT_ROUNDS` debe ser exactamente `8`. El logout es del lado cliente: elimina el token; el backend no mantiene lista negra, de acuerdo con la especificación.

Las rutas protegidas requieren `Authorization: Bearer <token>`. Las administrativas exigen `ADMINISTRADOR` o `RECEPCIONISTA`; las operaciones propias de cliente verifican propiedad.

## Reglas de negocio

- No se almacenan contraseñas en texto plano.
- Todas las entradas HTTP se validan con Zod.
- Precios, montos y cantidades respetan valores no negativos o positivos según corresponda.
- La fecha de salida debe ser posterior a la entrada.
- No se permiten reservas superpuestas.
- Una reserva tiene como máximo un pago.
- Un check-in requiere reserva válida.
- Un check-out requiere check-in y actualiza habitación y reserva.
- Una solicitud debe referenciar reserva, cliente y servicio existentes.
- Todas las consultas PostgreSQL son parametrizadas.

## Fases

1. Configuración TypeScript, Hono, PostgreSQL y variables de entorno.
2. Arquitectura de routes, controllers, middlewares, schemas, services y repositories.
3. Autenticación JWT, bcrypt y autorización por rol.
4. Habitaciones, clientes y reservas.
5. Check-in, check-out y pagos.
6. Servicios adicionales y solicitudes.
7. Dashboard y reportes.
8. Revisión de seguridad, compilación y ejecución.

## Criterios de aceptación

- El servidor inicia con TypeScript compilado y conecta con PostgreSQL.
- Login válido genera JWT y nunca expone contraseñas.
- JWT ausente, inválido o expirado devuelve `401`.
- Rol insuficiente devuelve `403`.
- Se gestionan habitaciones, clientes, reservas, pagos y servicios.
- Se bloquean conflictos de disponibilidad.
- Check-in y check-out sincronizan estados.
- Zod rechaza datos inválidos.
- Las consultas son parametrizadas.
- Se conserva Controller → Service → Repository.
